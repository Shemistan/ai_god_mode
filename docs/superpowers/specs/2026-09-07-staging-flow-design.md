# Поток `staging`: агент доводит задачу до PR сам


## Проблема

В исходном скелете задача заканчивалась пушем ветки `worktree-<task>` и
отчётом. Человек должен был сам вливать каждую ветку в `main`, а следующая
стадия многошаговой задачи стартовала от `main` и не видела результата
предыдущей. Для проектов вроде `it_news` (14 стадий подряд) это превращает
человека в узкое место после каждой стадии.

## Решение

Между задачами и `main` появляется интеграционная ветка **`staging`**, которая
принадлежит агенту:

```
main  ◀── PR (сливает человек) ──  staging  ◀── ff-push ──  worktree-<task>
                                       ▲
                                       └── база для следующего worktree
```

1. **Точка входа — голый `claude`** в корне проекта. Человек пишет задачу и
   больше ничего не запускает. Регламент `CLAUDE.md` («Старт задачи»)
   велит агенту: в main checkout первым действием сделать EnterWorktree
   (ветка `worktree-<slug>` от `main`), затем `git merge staging`, чтобы
   встать на результат прошлых задач. Preflight-хук каждый промпт напоминает
   об этом в контекст, пока сессия в main checkout.
2. **Подзадачи**: большую задачу агент декомпозирует сам; каждая подзадача в
   своей ветке от `staging` (`git switch -c <slug>/<подзадача> staging` в том
   же worktree), между подзадачами не останавливается.
3. **`./finish`** агент запускает из ветки подзадачи, когда она готова:
   рабочее дерево чистое, `./check` зелёный → создать `staging` от `main`,
   если её нет → подтянуть `origin/staging` (если ушла вперёд — обычный
   merge) → запушить ветку → fast-forward `staging` на `HEAD` → запушить
   `staging` → открыть или обновить PR `staging → main` через `gh`.
   Отказывает на `main`/`master`/`staging`.
4. **Финал**: когда весь объём выполнен, агент отдаёт отчёт со ссылкой на PR
   и просит проверить. **Человек** проверяет PR и сливает в `main` сам. Это
   единственная точка, где он нужен.
5. **`./ai <task>`** остаётся необязательным ярлыком: делает п.1 скриптом до
   старта сессии (гарантирует `staging`, создаёт worktree от неё, запускает
   `claude --worktree`). Повторный запуск открывает существующий worktree.

Почему регламент, а не скрипт: создать worktree и сменить cwd сессии умеет
только сам агент (EnterWorktree), хуки этого не могут. Если агент забудет
`git merge staging`, ошибка не фатальна: при наличии origin `./finish` сам
вливает `origin/staging` в ветку (обычный merge, при конфликте — стоп с
подсказкой); без origin отказывает («staging не предок HEAD») и просит
`git merge staging`.

## Что защищено, что нет

- `main`/`master` защищены как раньше: guard, `pre-push`, регламент.
- `staging` **намеренно не защищена**: агент пишет в неё сам. Переписывание
  истории (force-push, `branch -D`, `push --delete`) запрещено guard'ом для
  всех веток, включая `staging`. Продвижение `staging` в `./finish` только
  fast-forward: если она ушла вперёд, сначала merge в ветку задачи.
- `git branch -f staging <sha>` guard не блокирует (регекс ловит только
  `main|master`); `./finish` использует его лишь после проверки, что текущий
  `staging` — предок `HEAD`.

## Требования к окружению

- `gh` авторизован (`gh auth login -h github.com`), иначе PR не создаётся;
  `./finish` печатает предупреждение и не падает — ветки уже запушены.
- `gh` вынесен в `sandbox.excludedCommands` в `.claude/settings.json`
  проекта, поэтому работает мимо сетевого allowlist.
- Репозиторий без `origin`: `./finish` двигает локальную `staging`, пуш и PR
  пропускает с сообщением.

## Файлы

| Файл | Изменение |
|---|---|
| `ai` | (необязательный ярлык) проверка/создание `staging`, `git worktree add … staging` перед `claude --worktree` |
| `finish` | новый скрипт: создать `staging` при отсутствии → check → push ветки → ff `staging` → push → PR; любая ветка кроме main/master/staging |
| `CLAUDE.md` | раздел «Задачи и ветки»: старт через EnterWorktree + merge staging, подзадачи в своих ветках, `./finish`, критерий остановки |
| `.claude/hooks/preflight.sh` | напоминание в main checkout: EnterWorktree + merge staging (правит человек: каталог защищён от агента) |
| `new-project.sh`, `bootstrap.sh` | копирование и `chmod +x` для `finish` |
| `global/hooks/test_guard.py` | ALLOWED-кейсы для команд `./finish` |
| `README.md`, `SECURITY.md` | описание потока и оговорка про `staging` |
